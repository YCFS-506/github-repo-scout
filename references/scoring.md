# 评分细则（scoring）

> 代码在 `scripts/repo-audit.mjs`，本文件是它的口径说明书：每一项为什么这么算、怎么调、哪里不可信。
> **一句话原则：star 只在 100 分里占 2 分；"能不能用起来"占 70 分；"是不是正好解决你的问题"占 30 分。**

---

## 1. 权重总表

| 维度 | 默认权重 | 数据来源 | 谁来判定 |
|---|---|---|---|
| 功能匹配 `fit` | 30 | README 摘要 / 描述 / release notes（脚本给出证据，模型判定） | **模型必须自己判**（`--fit`），并附 ≥3 个来源；不判就按中位 15 估算并标 * |
| 可落地 `integrability` | 20 | 语言、release 产物、体积、topics、主页 | 自动 |
| 维护 `maintenance` | 15 | 最近提交、最近 release、发布节奏、**发行节奏变化** | 自动 |
| 文档 `docs` | 10 | README 体积、是否有安装/使用章节、是否中文 | 自动（要 `--readme`，默认开） |
| 生态 `ecosystem` | 10 | 贡献者（`--contributors`）、订阅者、fork | 自动（部分需采样） |
| 许可 `license` | 8 | SPDX 分类 | 自动 |
| 风险 `risk` | 5 | 停更/无许可/归档/疑似资料/issue 积压/单人维护 | 自动（扣分制） |
| 热度 `popularity` | 2 | star，对数缩放 | 自动 |

### 1.1 权重可覆盖，但 star 有硬上限

```bash
--weights fit-first        # 默认（通用选型）
--weights risk-averse      # 要上生产/长期维护：许可 12、风险 9、生态 6、文档 8、可落地 18
--weights quick-tool       # 只要个能跑的小工具：fit 35、风险 10、文档 12、维护 12、可落地 15
--weights "fit=40,license=12,popularity=0"   # 按维度覆盖，自动归一化到 100
```

实测效果（同一个候选池）：`risk-averse` 会把 AGPL 项目从第 2 名压到第 3 名（linkwarden 80.03 < loomark 80.41），
`fit=50,popularity=0` 则把差距完全交给功能匹配。

**硬上限：`popularity` 不允许超过 10。** 超了脚本直接拒绝执行：

```
✖ popularity=25 超过硬上限 10。
把 star 权重调到这个量级，结果就变成"star 排行榜"——恰恰是这个 skill 存在的理由（默认只给 2 分）。
```

要绕过必须显式 `--allow-star-heavy`，并且应当在报告里说明"这是有意为之"。**这条护栏是给工具本身用的：
它不能被配置成一个 star 排序器。**

### 1.2 功能匹配分的证据门槛

借自同类方案 `pi-skill-tech-deep-dive` 的"每个候选最少 3 个独立来源"：

| 情况 | 处理 |
|---|---|
| `sources` ≥ `--min-sources`（默认 3）且跨 ≥2 个域名 | 正常计入 |
| `sources` < 下限 | 该项**封顶 20 分**，表里标 `^`，证据段写明"⚠ 证据来源不足" |
| `sources` 全部来自同一域名 | 提示"独立性存疑"（一个 README 看三遍不算三个来源） |
| 加 `--strict-evidence` | 证据不足的条目**视为未提供**（退回中位 15 分 + 警告） |

典型来源组合：仓库页 + README + releases + 官方文档站 + 包管理器页（npm/PyPI/crates）+ Docker Hub + 第三方评测/基准。
**不要用同一个域名的三页凑数。**

## 2. 逐项算法

### 维护 15 = 提交新鲜度(≤9) + release 新鲜度(≤4) + 发布节奏(≤2)

> **为什么不用 star 增量做"势头"信号**：whichlib 用 7 日 star 增量当 40% 的权重，我们不学。
> 涨星快常常来自热点与营销，奖励的正是要压低的东西；而且它依赖每日快照数据源（本机实测不可达）。
> **替代方案**：用已经免费拿到的 release 数据算**发行节奏变化**（发行活跃 / 仍在发行 / 发行放缓 / 无发行记录），
> 这是 star-free 的势头信号，回答的是同一个问题——"这东西是在往上走还是往下走"。它只写进证据说明，不额外加分（避免与新鲜度重复计分）。

| 最近提交距今 | 得分 |
|---|---|
| ≤30d | 9 |
| ≤90d | 8 |
| ≤180d | 7 |
| ≤365d | 5 |
| ≤730d | 3 |
| ≤1095d | 2 |
| 更久 / 未知 | 1 |

release：≤180d → 4；≤365d → 3；更久 → 2；无 release 但仓库活跃 → 1；无 release 且不活跃 → 0。
发布节奏：最近 5 条 release 里 ≥3 条 → +2。

> 为什么不用 commit 数？大多数项目不规整地 squash，commit 数没有可比性。**提交新鲜度 + 发布节奏**更能说明"还活着且还在进步"。

### 可落地 20 = 语言(≤8) + release 产物(4) + 体积(≤4) + topics(2) + 主页(2)

- 语言：命中 `--target-lang` → 8；未声明目标栈 → 5（中位，不惩罚）；不匹配 → 1。
  *这一项比 star 权重高 4 倍：语言不对的项目对你就没有价值，哪怕 5 万星。*
- release 产物：有 release → 4（说明有可安装/可下载形态，不是只能 clone）。
- 体积：50KB–500MB → 4；<50KB → 2（可能只是个壳）；>500MB → 1（巨型单体）。
- topics → 2；有 homepage/docs 站点 → 2。

### 文档 10 = README 存在(≤3) + 安装/使用章节(≤4) + 体积合理(≤3)

- 只有 `--readme`（默认开）时才有区分度；拉不到或 `--no-readme` 时整项给中位 5。
- 安装/使用章节 = README 前 20KB 里出现 `## Install / Getting Started / Quick Start / Setup / Deploy / Usage / 安装 / 部署 / 使用 / 快速开始` 之一。
- 体积合理：1KB–200KB → 3；过长（>200KB，通常是翻译堆叠或自动生成）或过短（<1KB）→ 1。

### 生态 10 = 贡献者(≤5) + 订阅者(≤3) + fork(≤2)

- 贡献者（需 `--contributors`；未采样给 3.5 中位）：≥50 → 5；≥20 → 4；≥5 → 3；≥2 → 2；1 → 0。
- 订阅者 `subscribers_count`：≥200 → 3；≥50 → 2.5；≥10 → 1.5；其余 0.5。
  *订阅者（watch）比 star 难刷，是"真有人在意"的信号。*
- fork：≥200 → 2；≥50 → 1.5；≥10 → 1；其余 0.3。

### 许可 8

| 类别 | 例 | 分 |
|---|---|---|
| permissive | MIT、Apache-2.0、BSD、ISC、0BSD、Unlicense、Zlib | 8 |
| weak copyleft | MPL-2.0、EPL-2.0、LGPL | 6 |
| other | 其他 SPDX | 5 |
| strong copyleft | GPL-2.0/3.0、AGPL-3.0 | 3 |
| 许可不清 | `NOASSERTION` | 1 |
| 无许可 | — | 0 |

### 风险 5（从 5 扣起，扣到 0）

停更 >1y −2；停更 >6mo −1；无许可 −2；许可不清 −1；已归档 −1；疑似资料/清单/镜像/玩具 −1；未处理 issue >500 且 star <5000 −1；单一贡献者 −1。

### 热度 2

`2 × log10(stars+1) / log10(50001)`，上限 2。

| star | 该项得分 |
|---|---|
| 6 | 0.40 |
| 100 | 0.93 |
| 1,000 | 1.24 |
| 19,952 | 1.80 |
| 50,000+ | 2.00 |

**10 星和 5 万星的差距 = 1.6 分。而"语言不匹配"一次就丢 7 分，"功能只中一半"丢 15 分。**
这就是"不按 star 排序"的数学表达。

## 3. 功能匹配 `fit` 怎么打（0-30）

脚本给不出这一项，必须你自己判——判的依据是脚本输出的 README 摘要 + 描述 + release 信息。

### 三问（每问都要有证据）

1. **功能边界**：README 里明确写了哪些能力？对着 Phase 0 的验收标准逐条打勾/打叉。缺的能力是"没有"还是"有但没提"？（没提就当没有）
2. **部署/集成成本**：几个容器？要外部数据库/Redis/对象存储吗？要什么运行时版本？Windows 能不能跑？有没有 Docker/二进制发行版？（README 的 Install/Deploy 章节）
3. **项目状态**：单人还是团队/公司维护？issue 有人回吗？最近的 release 说明里在修 bug 还是在加功能？

### 打分锚点

| 分数 | 含义 | 典型证据 |
|---|---|---|
| 28-30 | 就是为这个需求做的，边界完全吻合，部署无障碍 | 功能项全中；Docker 一条命令；有 release；许可宽松 |
| 22-27 | 核心需求全中，有个别次要缺口 | 缺一个小功能，但可用脚本/插件补；部署需 2-3 个容器 |
| 15-21 | 只中一半，需要二次开发或胶水层 | 是相邻品类（例：要"稍后读"但它是"书签管理"）；需要自己写插件 |
| 8-14 | 只能借鉴架构/思路，不能直接用 | 是通用框架，你的场景要靠配置拼 |
| 0-7 | 名字像，其实用途不同 | 关键词撞车 |

**硬要求**：`fit < 22` 的候选进了首选/备选，必须在报告里给出**改造工作量量级**（半天 / 几天 / 需要重写某模块）。

### `--fit` 文件格式

```json
{
  "sissbruecker/linkding": {
    "fit": 27,
    "why": "自托管书签+归档，Docker 单容器；README 有 Install/Usage；验收标准 1/2/3 全中，4（全文存档）只到部分归档",
    "risk": "单人维护；无 Windows 原生版，需 Docker"
  }
}
```

- 键是 `owner/name`（大小写不敏感）。
- 未出现在 `--fit` 里的仓库按 15 分估算，并在表里打 `*`。
- 提供了 `--fit` 的仓库**一定会被深度体检**（即使超出 `--deep` 上限）。

## 4. 硬门槛（先淘汰再看分）

| 门槛 | 触发条件 | 放行开关 |
|---|---|---|
| 已归档 | `archived = true` | `--allow-archived` |
| 停更 | 最近提交 > `--max-idle-days`（默认 1095 天） | `--allow-stale` 或调大 `--max-idle-days` |
| 无许可（商用场景） | `--commercial` 且无 SPDX | `--allow-empty-license` |
| 明确拒绝的许可 | 命中 `--deny-licenses` | 从名单里去掉 |
| 空仓库 | `size = 0` | — |
| **内容倾倒仓库** | `content-dump` 标记：description 是 `.config`/JSON/HTML 文件内容（`Automatically generated file`、`Skip to content`、`<!DOCTYPE html>`、`{ "releases": {` 等特征），不是项目说明 | — （这不是项目，没有放行价值） |
| 仓库不存在 | 404（改名/删除/拼错） | 找新地址 |

**被淘汰不等于没价值**：报告第三节要列出被淘汰者与原因，用户可能想自己权衡（例如"停更但功能刚好够用"）。

### 4.1 为什么需要 content-dump 门槛（实测记录）

用泛化关键词搜索时（例：`desktop full text search engine`），GitHub 的 `sort=stars` 头部会混进大量**不是项目的东西**，且它们靠"关键词全中"拿到高分：

| 实测样本 | ★ | description 的真实内容 | 标记 |
|---|---|---|---|
| `zszszszsz/.config` | 359 | `# Automatically generated file; DO NOT EDIT. # OpenWrt Configuration` | `content-dump`, `idle>2y` |
| `Sfedfcv/redesigned-pancake` | 267 | 抓下来的 GitHub 页面 HTML（`Skip to content github / docs Code Issues 80...`） | `content-dump`, `empty-repo` |
| `klonnet23/helloy-word` | 92 | 倾倒的 release JSON（`{ "releases": { "2.0.4": [...] }`） | `content-dump` |
| `vohidjon123/google` | 44 | 倾倒的 Google 前端 JS（`(function(sttc){/* Copyright The Closure Library Authors`） | `content-dump` |

它们不仅污染候选池，还会污染 `hits` 信号（关键词全中 → 被多条检索式命中）。所以脚本对它们：候选池里标 `content-dump`、深度体检排序扣 15 分、风险扣 3 分、并在评分前直接淘汰；同时对整池发出**质量告警**（`gh-search` 的 `stats.pool_quality`），提示"该换词了"。

## 5. 分档

按**可得分上限的百分比**分档（`--no-deep` 浅层模式上限是 80 分，完整模式是 100 分，两者口径一致）：

| 百分比 | 分档 | 报告里的定位 |
|---|---|---|
| ≥80% | 首选 | 直接推荐，给最小验证步骤 |
| 68-79% | 备选 | 与首选对比：差在哪，什么情况下该选它 |
| 55-67% | 观察 | 值得读代码/借鉴某模块，或作为长期备胎 |
| <55% | 仅借鉴 | 只提"可参考它的 X 设计" |

## 5.1 浅层模式与"可比分"（配额不够时怎么用）

配额现实（匿名）：`search 10 次/分钟`、`core 60 次/小时`；深度体检每仓 4 请求（repo + releases + commits + README），**所以匿名每小时只能体检约 15 个仓库**。给个 token 能宽 10-80 倍。

两级打法：

1. **`--no-deep`（0 请求）**：只做浅层评分，先把排序跑出来。此模式下排序使用**可比分** = 总分 − 文档 − 生态（这两项需要逐仓采样才有区分度，不计入排序），满分 80。这一步还能白捡缓存里已有的体检结果。
   *为什么必须这么设计*：否则"先被体检的仓库"会因为拿到真实文档分（10/10）而排在"还没体检的仓库"（中位 5/10）前面——排序结果取决于体检顺序，这是不可接受的偏差。
2. **`--deep N`**：对挑出来的 N 个仓库补深度体检（含 README 摘要），再补 `--fit` 重跑（缓存命中，秒回）。

---

## 5.2 深度体检名额怎么分配（prelimScore）

`--deep N` 里的"前 N 个"不是按 star，而是按浅层分：

```
+8/+6/+3   多检索式命中（hits ≥3 / =2 / =1）   ← 相关性共振
+5/+4/+2   最近提交 ≤180d / ≤365d / ≤730d      ← 还活着
+4/+3/...  许可分类（宽松 / 弱 copyleft / ...）
+4/2/-1    语言命中你的栈 / 未声明 / 不匹配
+≤4        实体性下限 = min(4, 1.3·log10(stars+1))   ← 上限 4 分，只为不让 ★0 demo 吃光名额
+1         forks ≥ 3
-12/-15/-7/-5/-3/-6  归档·空仓库 / content-dump / awesome 清单 / 学习资料 / 镜像·玩具 / 商用场景无许可
-4/-2      ★0 且体积 <200KB / ★<3 且体积 <60KB     ← 拒绝"随手传的 demo"
```

注意这里 star 最多影响 4 分（且需要 5 万星才拿满），而 `content-dump` 一次扣 15 分——**名额永远先给"像真项目的东西"，而不是"星多的东西"**。

## 6. 已知偏差与免责（写报告时可以照抄）

1. **`docs`/`ecosystem` 有中位分**：未采样的候选在这两项拿中位分，所以浅层候选（未深度体检）的总分**只用于排序参考**，不能用于最终决策。
2. **`flags` 是启发式**：靠命名/描述/体积猜的，"疑似教程""疑似清单"可能误判，必须复核。
3. **stars/forks 是快照**：脚本缓存 6 小时以内视为新鲜；跨天决策请 `--no-cache` 重跑。
4. **`open_issues` 不等于 bug 数**：有些项目把它当论坛用，只看数字会误判，要看最近 issue 有没有人回。
5. **非 GitHub 生态不在池子里**：Codeberg/GitLab/npm 独占的项目需要 `web_search` 补充（见 `search-patterns.md` 第 6 节）。

## 7. 按场景调参

| 场景 | 怎么调 |
|---|---|
| 闭源商用 / 要嵌进产品 | `--commercial --deny-licenses "AGPL-3.0,GPL-3.0"`，许可权重被放大为硬门槛 |
| 要长期维护的底座 | `--contributors`（看 bus factor）+ `--max-idle-days 365` |
| 只要个能跑的小工具 | `--max-idle-days 1095 --deep 15`，允许"冻结但可用" |
| 语言必须一致 | `--target-lang "Rust"`，语言不匹配直接丢 7 分 |
| 想批量对比同类 | `--repo a/b --repo c/d ...` 跳过检索，直接体检 |
| **配额见底（匿名 core 60/hr）** | 先 `--no-deep` 看可比分排序（0 请求），再 `--deep 6` 体检挑出来的；配 token 最省事 |
| 想换权重 | 直接改 `scripts/repo-audit.mjs` 顶部的 `WEIGHTS` 与各项函数，或改 `--target-lang` 等开关（不要通过"改 star 权重"来偷懒——那正是本 skill 要消灭的做法） |
