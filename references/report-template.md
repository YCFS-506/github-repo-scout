# 交付报告模板（report-template）

> 报告是给**人**看的，不是把脚本输出粘一遍。
> 结构固定七节，**第三节（高星落选）和第四节（低星入选）是本 skill 的立身之本，缺了就等于退回"按 star 推荐"。**

---

## 模板

```markdown
# <需求一句话>：开源方案选型

## 一、需求画像

- 要解决的事：<一句话>
- 交付形态：<CLI / 库 / 自托管服务 / 桌面 GUI / 浏览器扩展 / 参考实现>
- 运行环境：<Windows / Docker / Linux / 浏览器>
- 技术栈：<...>
- 硬约束：<离线 / 私有化 / 闭源商用 / 体积 / 依赖越少越好>
- 验收标准：<1. ... 2. ... 3. ...>
- 排除项：<不要什么>
- 检索覆盖：<N 条检索式（中英各半）、覆盖 best/name/stars/updated 四种排序、候选池 M 个（其中 star<200 的 K 个）>

## 〇、结论（先说要紧的）

**判定**：<✅ 有强匹配 / ⚠ 没有强匹配> —— 判据是 `功能匹配 ≥22 且进首选/备选` 档。

- 若有强匹配：<一句话给出首选 + 它赢在哪>
- 若没有：**直说"没有合适的现成方案"**，转给自建路线 + 可借鉴的模块，不要为了让报告好看而硬推一个。

## 二、适配榜（按适配度，不按 star）

| 名次 | 分档 | 项目 | 适配分 | 功能匹配 | 定位一句话 |
|---|---|---|---|---|---|
| 1 | 首选 | [owner/name](url) ★<stars> | <score> | <fit>/30 | ... |
| 2 | 备选 | ... | ... | ... | ... |
| 3 | 观察 | ... | ... | ... | ... |

### 1. <owner/name> — 首选

- **它是什么**：<一个句子，来自 README 而不是你的想象>
- **为什么适合你**（对着验收标准逐条对）：
  - 验收标准 1 → ✅ <证据：README 哪一节 / 哪个功能>
  - 验收标准 2 → ✅ ...
  - 验收标准 3 → ⚠️ <缺口 + 影响>
- **代价与风险**：<许可 / 部署复杂度 / 单人维护 / 平台限制 / issue 积压>
- **项目状态**：最近提交 <日期/距今天数>；最近 release <tag @ 日期>；贡献者 <n>；订阅者 <n>；许可 <SPDX>
- **最小验证步骤**（<来源：README 的 Install 章节 / release notes>）：
  ```bash
  # 3-5 行以内，能让人今天就跑起来
  ```
- **它的短板**：<一句话，别只讲好话>

### 2. <owner/name> — 备选
（同上结构；并写清"什么情况下该选它而不是首选"）

### 3. <owner/name> — 观察/备胎
（同上结构，可精简）

## 三、高星但没选的项目（只看 star 会选错的地方）

| 项目 | ★ | 为什么没选 |
|---|---|---|
| [owner/name](url) | 19952 | 功能只覆盖需求的一小部分；部署要 4 个容器 + 外部数据库；AGPL 与闭源集成冲突 |
| [owner/name](url) | 1856 | 停更 2.5 年（已归档），依赖的上游库已不可用 |
| ... | | |

> 至少列 3 个；若 star 榜首就是首选，也要说明"它凭什么赢过其他高星候选"。

## 四、低星但入选的项目（只看 star 会漏掉的地方）

| 项目 | ★（star 榜名次） | 赢在哪 |
|---|---|---|
| [owner/name](url) | 17（第 20 名） | 唯一同时满足"离线 + 单文件部署 + 中文 OCR"的候选；活跃提交；MIT |

## 五、被硬门槛淘汰的（以及为什么你应该知道）

| 项目 | ★ | 淘汰原因 | 是否值得例外 |
|---|---|---|---|
| ... | ... | 停更 1803 天 | 否，依赖的上游已下线 |

## 六、兜底：如果没有合适的

（若存在）**目前没有能直接满足全部验收标准的现成项目。** 建议：
- 自己写：<技术路线 + 工作量量级>
- 借鉴：[A](url) 的 <模块>、[B](url) 的 <设计>
- 组合：[C](url) 做 X + [D](url) 做 Y，用 <胶水方式> 串起来

## 七、下一步

1. 建议先验证：<哪个项目 + 哪条命令>

## 写作纪律

1. **每条断言带出处**：功能来自 README 哪一节、状态来自哪个字段。写不出来就别写。
2. **不吹**：首选也要写短板；`fit < 22` 必须写改造工作量量级。
3. **不堆砌**：适配榜最多 5 个，候选池另附文件，别把 52 个仓库全贴进聊天。
4. **结论先行**：第一句就说"推荐哪个、为什么"，再展开论证。
5. **区分事实与推测**：README 没写的写"未见说明"，不写"应该支持"。
6. **说清代价**：每个推荐都要有"你会付出什么"（容器/数据库/学习成本/许可/平台限制）。
